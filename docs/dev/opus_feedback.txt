Okay. I've read the actual code (lib/*.ts), the full DESIGN.md, the addendum, the embedding decision, and the plugin/skill surface. Here's my honest read — first-time eyes, no deference to the session history.

The concept: strong, with one unexamined assumption

The claude-mem separation is the best idea here. "Normative knowledge (what you learned) vs. observational history (what you did)" is a real distinction that most memory tools blur, and getting it right upfront is worth a lot. The proactive framing — context appears instead of being searched for — is the right north star.

But there's a load-bearing assumption the whole design rests on and barely interrogates:

That injecting context on every prompt is net-positive.

Irrelevant injected context isn't free — it dilutes attention and can actively degrade answers. The design treats retrieval as always-beneficial and gates only on a similarity threshold... which you've already documented as unreliable and model-dependent. So the one safeguard against "inject noise into every prompt" is the mechanism you've flagged as untrustworthy. There's no discussion anywhere of when not to inject — "fix this typo" gets the same 1-3k token treatment as "how should I structure error handling." That's the biggest risk to the concept and it's the least explored.

"Tokens saved" is a vanity metric

The status dashboard leads with "tokens saved vs. full-file injection." But nobody's baseline is "inject whole files" — it's "inject nothing" or "the old MEMORY.md scan." Measuring against full-file injection is a strawman that makes contextus look good by ow a big number.

The metric that actually matters is the v2 deferred one: did the injected cohe better? (use_count vs hit_count). That's not a nice-to-have — it's the only honest measure of whether this works, and it's pushed to v2 while three dashboards ship around a number that can't go down. I'd promote "used vs. retrieved" to the core loop and let
the vanity metric go.

The design has outrun validation

This is the thing I'd most want you to hear: ~1,400 lines of design + 10 ski observability dashboards, sitting on ~4 stub files and zero workingretrieval.

- chroma-client.ts / embedder.ts are plain JS in .ts clothing — no types, MiniLM hardcoded despite nomic being "the decision," default path still .claude/context-db (pre-migration).
- No daemon, no chunking, no re-ranking, no compression, no hit tracking — aist only in prose.
- You're designing /context-calibrate's optimization suggestions before a single retrieval has happened.

The riskiest hypothesis (above) has the most machinery built on top of it and the least evidence under it. I'd stop designing and run a dead-simple spike: embed the corpus, inject
top-3 raw, use it for a week, manually judge whether injections helped. Then/re-ranking are worth building. Right now you're optimizing a pipeline whosecore value is unproven.

A likely real bug in the foundation

new ChromaClient({ path: resolve(dbPath) }) — the JS Chroma client's path is a server URL, not an embedded file path. True embedded/file mode is a Python-client thing; the Node client
has historically needed a running Chroma server. "File-based ChromaDB with npremise that doesn't hold for the JS client. Verify this before anything else — it could invalidate the "no external service" selling point and the entire daemon-owns-Chroma design. (Worth a 30-min spike on its own.)

Tension you haven't resolved: capture volume vs. retrieval quality

The addendum says "more noise is acceptable" for capture (opt-out, propose on ANY new detail). But you also note that session-written patterns often capture conversational fluff, not
durable rules — and that retrieval quality is what makes the whole thing wor directions: aggressive capture → noisier corpus → worse retrieval. Garbagein, garbage out, on every prompt. The propose/auto modes and dedup threshold are partial answers, but the strategy is "capture lots, sort it out later" and "later" is the deferred
quality loop.
